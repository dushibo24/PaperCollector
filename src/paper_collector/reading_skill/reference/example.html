论文结构与写法

全文按「模型能力已经超出旧基准 → 真实软件工程既难又可用测试验证 → 用三级过滤把 PR 变成任务 → 定义补丁与判分 → 在两种检索设置下测模型 → 从低分里拆出瓶颈」推进。第 1 节用「基准饱和 + 代码任务可验证」立论；第 2 节把构造管线、任务形式、指标与数据特性一次讲完；第 3 节介绍自己微调的 SWE-Llama；第 4 节交代检索与输入格式；第 5 节报告主结果、上下文消融与定性分析；第 6、7 节收束到相关工作与局限。真正的工作量在附录 A：把每个过滤阶段的保留量、字段定义、执行校验与 Lite 子集逐项写清楚。

第1节 引言：现有基准饱和；代码生成题太短；真实仓库修复既难又能跑测试验证 第2.1节 构造：12 个热门 Python 仓库 93,139 条 PR → 属性过滤 11,407 → 执行过滤 2,294 第2.2节 任务：输入 issue 文本与完整代码库，输出 patch；应用成功且测试全过才算解决 第2.3–2.4节 特性：真实、可更新、长输入、跨文件编辑；另出 300 条 Lite 子集 第3节 训练集与模型：37 个仓库 19,000 条 → 过滤后 10,000 条；LoRA 微调 CodeLlama-Python 7b/13b 第4节 设置：BM25 检索与 oracle 检索；ChatGPT-3.5、GPT-4、Claude 2、SWE-Llama 第5节 结果：Claude 2 在 BM25 下 1.96%，oracle 下 4.80%；上下文越长反而越差 第5.1节与附录F 分析：定位错误、补丁过短、只改单文件；案例逐行对照

写法上有四个值得借鉴的安排。第一，把「数据构造」本身当作方法：三级过滤每一级都给保留数量，读者能判断 2,294 条来自 9 万多条的逐层筛选。第二，主结果与「oracle」结果并排：前者代表真实可部署的检索，后者代表「已经知道该改哪些文件」的上界，两者的差距直接把瓶颈指向代码定位。第三，不只报一个总分，还按仓库、按输入长度、按补丁长度拆开；每个拆分都对应一条可检验的解释。第四，附上训练集与微调模型，让开源模型也能进入同一张表；这让「数据集」同时成为「训练资源」与「评测标尺」。

写法分析为本笔记归纳，论文本身没有单列「写作结构」一节。

02

故事线：为什么非做不可

背景与重要性。语言模型已经进入聊天、编程助手与自动化工作流，模型能写出的代码越来越长，但评测还停在「给小函数补全几行」的尺度。HumanEval 一类基准题目自包含、几十行就能解完，和真实软件工程差距很大：修一个 bug 往往要先在几千个文件里找到相关函数，再理解跨文件调用关系，最后改几行并保证旧功能不坏。如果评测不进入真实仓库，模型能力的上限与短板都无法被看清。

相关工作的不足。论文把已有评测分成两类并指出缺口。通用能力基准（MMLU、BIG-bench、HELM）覆盖广，但每个任务只考一两个技能，题目偏短，难以给出「能不能完成一次真实工程任务」的判断。代码生成基准（HumanEval 及其多语言、多测试扩展）可执行、可判分，却把编辑范围限制在单个函数或闭包填空，模型不需要定位、不需要读整个仓库、不需要维护旧测试。软件工程领域已有自动修复与补丁生成研究，但数据规模、任务真实度与统一评测口径都不够。

挑战。把 GitHub 变成基准要同时解决四件事。第一是数据质量：仓库、issue 与 PR 充满噪声，很多 PR 没有关联 issue，很多修复没有补测试，直接爬下来会把「无法验证的改动」混进数据。第二是正确性判定：代码补丁不能靠文本相似度打分，必须真的应用、真的安装依赖、真的跑测试。第三是上下文规模：一个仓库平均 3,010 个非测试文件、43.8 万行代码，远超当时多数模型的上下文窗口，必须设计检索。第四是可复现性：仓库会更新、依赖会漂移、测试会失效，任务必须绑定到确切的 base commit 与运行环境。

解决方式。作者设计三级过滤。第一步选 12 个热门且以 Python 为主的开源仓库，抓取全部 PR；第二步只保留「已合并、关联并解决 issue、修改了测试文件」的 PR；第三步在真实环境里先装依赖，再把测试补丁与其他改动分开应用，记录每个测试在改动前后的状态，只保留至少有一个测试从失败变成通过的样本。通过三级过滤的 2,294 条 PR 被转成统一任务：代码库由 repo 与 base commit 还原，问题描述由关联 issue 的标题、正文与评论拼接，参考解与隐藏测试都存成 patch。判分时把模型补丁应用到代码库，运行 fail-to-pass 与 pass-to-pass 测试；补丁应用成功且测试全过，才算解决。

贡献。论文的贡献可以归成四项。第一，提出一个从真实 PR 自动构造软件工程任务的管线，并给出每一级的保留量。第二，发布 2,294 条跨 12 个仓库的任务，附完整的执行评测环境与字段定义。第三，发布 19,000 条训练样本与 SWE-Llama 7b/13b，让开源模型能进入同一张表。第四，用 BM25 与 oracle 两种检索、按仓库与上下文长度的拆分、以及逐例定性分析，把「模型不会修真实 bug」拆成可操作的瓶颈。

把这条链压成一句：模型能力超出旧基准 → 真实仓库修复既难又能用测试验证 → 从 9.3 万条 PR 三级过滤出 2,294 条 → 用补丁应用与测试全过判分 → Claude 2 只解出 1.96% → 瓶颈在定位、长上下文与跨文件修改。

从 PR 到任务怎样落地

从输入到判定

输入
一条 issue 聚合文本（标题、正文、PR 首次提交前的相关评论），加上 BM25 检索出的若干代码文件与文档，再加任务说明与一个 patch 格式示例。oracle 设置下，检索结果换成参考解实际修改过的文件。
输出
一个 unified diff 格式的补丁，声明要改哪些文件、哪些行、增加与删除什么。
判定
用 unix patch 应用补丁；应用成功只是前提，之后还要运行该任务的 fail-to-pass 测试与 pass-to-pass 测试。补丁应用成功且所有测试通过，记为 resolved。
指标
% Resolved：解决任务的比例。另有 % Apply：补丁能成功应用的比例，用来区分「格式不对」与「改错了」。

第一步：三级过滤把 PR 变成任务

Figure 2 把构造管线压成三个框：抓 PR、按属性过滤、按执行结果过滤。三个框对应论文 2.1 节的三级筛选，每一级都有明确的通过条件，且都可以在没有人工标注的情况下自动执行。

三个从左到右的圆角框：① Scrape PRs——12 popular repositories、>90% Python Code；② Attribute Filter——Resolves an issue、Contributes tests；③ Execution Filter——Installs successfully、PR passes all tests。箭头表示逐级筛选。

第一级解决「从哪里来」：只取热门、以 Python 为主、许可证允许使用的仓库，保证文档、测试与维护质量。第二级解决「是否可验证」：PR 必须关联并解决 issue，且改动过测试文件，说明作者自己提供了验证手段。第三级解决「是否真的修好」：在隔离环境里安装依赖，把测试补丁先应用、再应用参考解，要求至少一个测试从失败变为通过。三个框合起来把「有问题的真实改动」变成「有隐藏测试的可执行任务」。

图中没有写每级的淘汰率；正文只给最终数 2,294，精确的逐级数量在附录 Table 10。属性过滤依赖关键词（如 fixes、closes）识别 issue 关联，会漏掉没有写关键词的 PR；执行过滤依赖测试环境，装不上的样本会被直接丢掉，可能系统性排除依赖复杂的仓库。

第四步：代码库放不进上下文，怎样检索

平均 43.8 万行代码不可能整份塞进模型，作者比较两种上下文来源。BM25 是真实可部署的稀疏检索：用 issue 文本当查询，按词项匹配召回文件，尽量填满上下文预算。oracle 是分析用的上界：直接给出参考解实际修改过的文件，模拟「已经知道该看哪里」。两者的差距，用来衡量「检索找错文件」对最终成绩的影响。

Table 3 给出 BM25 相对 oracle 文件的召回率。13k 上下文时，平均只召回 29.58% 的 oracle 文件，至少召回一个文件的比例是 34.77%；把预算加到 50k，平均召回升到 51.06%，仍有近一半 oracle 文件没被找到。这解释了后文一个重要现象：上下文变长会提高召回，却不一定提高解题率。

列是三个最大上下文长度 13k、27k、50k；行是三种统计口径：Avg.（平均召回率）、All（oracle 文件全部被召回的比例）、Any（至少召回一个 oracle 文件的比例）。

从 13k 到 50k，Avg. 从 29.58 升到 51.06，All 从 26.09 升到 45.90，Any 从 34.77 升到 58.38。三行都随预算上升，说明检索确实能从更多上下文里找到更多相关文件；但即使 50k，仍有过半任务没有找全参考文件。All 与 Any 的差距说明「找到一个相关文件」比「找全所有相关文件」容易得多，而跨文件修复往往需要后者。

召回是相对 oracle 文件计算的，oracle 文件本身不一定包含解题所需的全部上下文；召回率高也不代表模型能用好这些文件。BM25 只匹配词项，不理解代码结构，对命名不直观的函数天然不利。

论文从结果里提炼的五条发现

第一，基准远未饱和。最好的 Claude 2 在真实检索下只解出 1.96%，Claude 3 Opus 也只有 3.79%；即使把 oracle 文件直接给出，Claude 2 也只有 4.80%。这与 HumanEval 上动辄八九十分的表现形成强烈反差，说明「会写函数」离「会修仓库」还有很长距离。

第二，检索与定位是主要瓶颈之一。BM25 在 13k 下平均只召回 29.58% 的 oracle 文件；从 BM25 换到 oracle，Claude 2 从 1.97% 升到 4.80%；再把文件折叠到改动行 ±15 行，Claude 3 Opus 升到 9.39%。三种设置形成一条清晰的阶梯：找到文件、找到行、改对逻辑，每一步都在掉分。

第三，更多上下文会伤害表现。Table 2 中三个模型都在 13k 最好，50k 时 SWE-Llama 归零；Figure 5 显示输入超过 100k 后 Claude 2 的解决率接近 0，而 issue 长度本身没有同样效应。作者把原因指向无关代码的干扰与长上下文中的定位困难。

第四，模型补丁偏短、偏局部。模型平均只改约 20 行、1 个文件，参考补丁平均改 32.8 行、1.7 个文件；模型新增 1.3–4.4 行，参考补丁新增 8.4–12.0 行。模型倾向于「让眼前测试过」，缺少参考解那样的结构性修改与防御性处理。

第五，格式能力与语义能力要分开看。SWE-Llama 13b 的补丁应用率 53.62%，高于 Claude 2 的 43.07%，但解决率只有 0.70%；Claude 2 应用率更低，解决率更高。Figure 6 的案例进一步说明，模型可以定位到正确函数并写出合法 diff，仍然改错配置分支。用单一成功率无法区分这两类失败。

原文定位：PDF p.5–p.9；发现为本笔记按论文数据归纳，论文原文以分节讨论呈现。

把这些证据合起来，能说到哪一步？

能站住的主张有五个。第一，SWE-bench 有明显区分度：BM25 下从 ChatGPT-3.5 的 0.17% 到 Claude 3 Opus 的 3.79%，oracle 下从 0.52% 到 4.80%，折叠上下文后到 9.39%；分数跨度足够大，没有把所有模型压到同一档。第二，任务确实跨文件、跨函数：参考补丁平均改 1.7 个文件、3.0 个函数、32.8 行，且 40% 的任务至少有两个 fail-to-pass 测试。第三，评测可执行、可复现：任务绑定 base commit，补丁必须应用成功并跑过真实测试，这比文本相似度或人工打分更硬。第四，瓶颈可以定位：检索召回、上下文长度、补丁长度与定性案例四组证据指向同一个结论——模型在「找对位置」与「改对语义」上都不够。第五，数据集同时是训练资源：37 个仓库的 19,000 条样本让 SWE-Llama 在 oracle 下达到 3.97%，接近 Claude 2 的 4.80%。

论文不能支持的主张也要说清楚。第一，没有人类基线：全文没有报告人类工程师在 2,294 条任务上的解决率或耗时，1.96% 只能与模型池内部比较，无法回答「离人类还有多远」。第二，任务全部是 Python，且来自 12 个热门、测试完善的大仓库；结论不能外推到其他语言、小项目或私有代码库。第三，判定只看测试是否通过：测试覆盖不到的 bug、风格问题、性能回退都不会被发现；论文自己在讨论中也承认，自动生成的补丁可能在可读性、效率与完整性上不如人类。第四，检索设置与模型版本强耦合：BM25 是 2023 年的基线，换成更强的检索或 agent 式多轮探索，分数会变；论文没有给出检索器消融之外的系统对比。第五，没有多次运行与置信区间：seaborn 22 条、flask 11 条，逐仓库分数很容易被单条任务左右；GPT-4 只在 25% 子集上评测，跨模型比较并不完全同分布。第六，训练集与评测集仓库不相交，但模型预训练语料可能包含这些公开仓库；作者用「2023 年前后」的时间切分做了检查，发现多数模型差异不大，但 GPT-4 在 2023 年后的样本上为 0，样本量也小，不能完全排除记忆效应。第七，环境可复现性依赖依赖版本与镜像，几年后部分任务可能装不上；论文提供镜像与脚本，但没有承诺长期维护。

本篇评测口径

测试集构造：从 PyPI 2023 年 8 月下载量前 5,000 的包中取前 100 个，核对许可证后确定 12 个 GitHub 仓库，抓取全部 PR 共 93,139 条。属性过滤要求 PR 已合并、通过 fixes/closes 等关键词关联并解决至少一个 issue、且修改了路径含 test/testing 的文件，剩 11,407 条。执行过滤要求在隔离环境安装成功，先应用测试补丁、再应用参考解，至少有一个测试从失败变为通过，且无安装/运行错误，最终剩 2,294 条。另有 300 条 Lite 子集，覆盖 11 个仓库，偏向自包含的功能性修复。

成功判据：把模型补丁用 unix patch 应用到 base commit 的代码库；应用失败直接判未解决。应用成功后运行该任务的 FAIL_TO_PASS 与 PASS_TO_PASS 测试，前者必须全部由失败转为通过，后者必须保持通过；全部满足才记为 resolved。指标是 resolved 任务数除以总任务数。补丁应用成功但测试失败，只计入 % Apply，不计入 % Resolved。

输入与检索：输入包含任务说明、issue 聚合文本、检索到的代码文件与文档、一个 patch 格式示例。主设置用 BM25 稀疏检索，按 issue 文本召回文件，最大上下文取 13k、27k、50k 三档；分析设置用 oracle（参考解修改过的文件）与 oracle-collapsed（只保留改动行 ±15 行）。

模型与预算：ChatGPT-3.5（16,385 token）、GPT-4（32,768 token）、Claude 2（100,000 token）、SWE-Llama 7b/13b（≥100,000 token）。SWE-Llama 用 CodeLlama-Python 初始化，LoRA 微调，训练集来自另外 37 个仓库的 19,000 条样本（截断后 10,000 条）。

基线：没有人类基线。比较对象是上述模型在 BM25、oracle 与 oracle-collapsed 三种设置下的结果。主结果的最佳值是 Claude 2 的 1.96%（BM25）与 4.80%（oracle）；Lite 上最佳是 Claude 3 Opus 的 4.33%。

适用范围：Python、公开 GitHub 仓库、英文 issue、单轮生成补丁；不覆盖多语言、私有代码、多轮交互式调试、代码审查与性能优化。

仍应保留的边界

（1）全部任务都是 Python，且只来自 12 个热门、测试完善的开源仓库；小项目、私有代码、其他语言与遗留系统都不在覆盖范围内。（2）判定完全依赖仓库自带测试，测试覆盖不到的 bug、性能回退、可读性与安全问题不会被发现；论文自己也承认，通过测试不等于补丁质量高。（3）没有人类基线，也没有多次运行与置信区间；1.96%、3.79%、4.80% 这些数字只能做模型间相对比较，不能直接解读为「完成真实工作的概率」。（4）检索设置强依赖 BM25 与固定上下文预算，换成更强的检索器、agent 式多轮探索或仓库级代码索引，结果会显著变化；论文没有给出这些替代方案的对比。（5）GPT-4 只在 25% 子集上评测，SWE-Llama 训练与评测的上下文分布不一致，跨模型排序存在混杂因素。（6）oracle 与 oracle-collapsed 使用了参考解信息，现实中不可得；它们衡量的是「定位之后」的能力，不是端到端上限。（7）仓库会更新、依赖会漂移，任务绑定 base commit 与镜像只能延缓失效；论文没有给出长期维护与版本化评测的机制。（8）公开仓库可能进入模型预训练语料，时间切分只能提供有限证据；2023 年后的样本量小，无法排除记忆与污染。（9）任务在仓库间高度不均衡：django 850 条、flask 11 条，按任务平均与按仓库平均会得到不同结论；逐仓库分数对小样本仓库尤其不稳。
