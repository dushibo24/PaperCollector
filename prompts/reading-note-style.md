# 参照 Incalmo 笔记的讲解方式

读者需要一位带着走的讲解者，不需要一张填满了的审稿表。
写得清楚不等于删掉技术细节；关键是先给细节一个能理解的位置。

## 先放一个读者看得见的问题

Incalmo 的笔记先讲：入口是外部 Web 服务器，目标却在另一个网段；
凭据在机器 A，数据库在机器 B，必须经过跳板。读者由此理解“多主机”到底多了什么困难。
随后才引入规划器、专家代理和状态服务，每个部件都在回答刚才暴露的问题。

反例：“该模型利用结构化递推实现可控选择性，并建立表达力分离。”
这句话可以出现在已经讲懂后的总结里，不能承担第一遍讲解。
正例：“同一个符号第一次出现时，要记住它后面的内容；再次出现时，要把记住的内容答出来。
如果决定要不要写入的开关只看眼前的符号，它怎么区分这是第一次还是第二次？”
这个例子只是讲解手法；当前论文的任务、条件与结论仍以提供的原文为准。

## 每一步接住上一步

Incalmo 先扫描发现入口，再感染主机，再查找凭据，再跨网段进入数据库。
每一步都说明已有的东西、新做的动作和留下的结果。不要写成五个没有因果关系的组件简介。
理论论文也一样：先说要证明什么，用哪个反例或构造，关键一步为什么成立，最后才回到定理。

## 一句话只承担一个转折

“LLM 决定做什么，领域代码负责怎么做。”这句话易懂，因为前面已经说明了任务和执行的区别。
不要把多个数学限定、英文缩写、参数量和实验结果塞进一个长句。
不要机械换成口语：删除一个词后若读者仍不知道它指什么，这个词就还没有解释清楚。

## 读图是继续讲故事

先指出图上最值得看的位置，再解释比较对象和差异，最后说明这条证据支持到哪里。
次要读数、完整配置和核查记录放在补充材料；正文不反复复述相同结论。

## 写完后的读者检查

- 第一屏能否直接回答：在解决什么问题，为什么旧办法不够，作者改了什么？
- 不懂作者缩写的人，能否跟着一个完整例子把方法走完？
- 每个公式和数字前是否已经有了读它的理由？
- 删除摘要、主线或正文中的任意一段重复介绍，会不会毫无信息损失？能删就删。
- 标题是否提出具体问题或说明具体变化，而不只是“技术细节”“关键机制”“结果与解释”？

没有目标字数。只检查说明是否清楚、证据是否可靠、是否值得继续读。
